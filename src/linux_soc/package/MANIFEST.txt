 ADDENDUM 2026-07-16 (plan-D v2: the tick-death fix)
========================================================================
Plan-D board result: SEIP IS ALIVE ("pland: first tick via SEIP
delivered" at 0.021 s) and ticks flowed for ~33 s of rc scripts -- then
stopped (dmesg stamps bunch at 32.89, console froze mid-write, jiffies
dead while rdtime advanced). Diagnosis: stale-latch loss in the level
ack flow. handle_level_irq acks the intc IAR BEFORE the ISR runs; the
ISR's T0INT source-clear is a posted AXI write, so the still-high input
re-latches the axi_intc LVL_P bit (sticky until IAR). v1 relied on a
spurious re-entry to flush that stale latch; real silicon timing loses
that dance eventually (order 10^3..10^4 ticks) and the line wedges with
no further edge for the latch to see = tick death.

Fix (sw/Image_pland REPLACED, v2, sha ed3f9749..d7d7f23; DTBs
unchanged): the ISR now uses the plan-C-v2-proven ack sequence in
S-mode: W1C T0INT + READ BACK (source provably low), then an explicit
IAR write scrubbing our own re-latched ISR bit + read back, so the late
unmask always finds a clean latch -- deterministically one interrupt
per tick. The extra IAR only W1Cs our own bit; kernel irq bookkeeping
unaffected. The IRQ_NONE guard remains as a counted backstop.
Instrumentation (once-only): "10 ticks via SEIP (spurious re-latch
backstops: N)" and "2500 ticks via SEIP, tick engine stable" (~10 s at
HZ=250 -- past the previous death point; if it prints, the fix held).
Off-board proof limits (honest): the stale-latch race needs real AXI
posted-write timing -- QEMU cannot reproduce it (and cannot deliver
SEIP at all). Verified instead: qemu-virt regression PASS with this
exact Image; QEMU-MBV probe path prints "latch scrub on" (intc mapped
via interrupt-parent); image_size unchanged (112 KiB DTB margin holds).

Board result on the v6 login stack (irquart): prompt + "Password:" appear
(v6 getty->login prompt fix confirmed), then getpass() stalls after
"Password:" (hart alive, blocked in read). Root cause: canonical single-
byte getpass read (libbb/bb_askpass.c keeps ICANON, clears only ECHO) over
the irquart In1 path hits an edge-pulse-into-LEVEL-intc lost-interrupt race
(a keystroke landing in the ulite_isr-drain -> IAR window leaves the char
in the FIFO with no new edge) -- the In1 analog of the v4.1 In0 timer bug;
racy, so username usually gets through and password hangs. crypt/auth are
FINE (block is in read()).

rx-poll DTB, whose 20 ms FIFO poll is immune to the race:
