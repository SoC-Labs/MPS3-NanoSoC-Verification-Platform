# RETRACTED: "ethmac TX-length bug" — the MAC is CORRECT. The register map is wrong.

**This file previously claimed the OpenCores ethmac ignored the buffer-descriptor length
and ran every frame to MINFL/MAXFL. That claim is WRONG and is retracted.** The MAC is
faultless. The real defect is in the **register description**, and it is a genuine,
on-board-affecting bug — just not the one I originally reported.

## What actually happens

`PACKETLEN` (0x018) is, per the RTL (`eth_registers.v:926-927`):

```verilog
assign r_MinFL[15:0] = PACKETLENOut[31:16];   // MINFL is the UPPER half
assign r_MaxFL[15:0] = PACKETLENOut[15:0];    // MAXFL is the LOWER half
```

The reset value settles it beyond argument — `PACKETLEN` resets to **`0x00400600`**:

| bits | value | field | sane? |
|---|---|---|---|
| [31:16] | `0x0040` = **64** | MINFL | ✅ the Ethernet minimum frame length |
| [15:0] | `0x0600` = **1536** | MAXFL | ✅ the Ethernet maximum frame length |

## The bug: the generated register header has the fields TRANSPOSED

`ethernet-mac-ahb/src/sw/ethmac_regs.generated.h` (generated by `scripts/rdl2c.py` from the
`ethmac_regs` addrmap) says the exact opposite:

```c
#define ETHMAC_REGS_PACKETLEN_MINFL_Pos   0U       /* claims MINFL is [15:0]  */
#define ETHMAC_REGS_PACKETLEN_MINFL_Rst   0x600U   /* "minimum" frame length = 1536 ?! */
#define ETHMAC_REGS_PACKETLEN_MAXFL_Pos   16U      /* claims MAXFL is [31:16] */
#define ETHMAC_REGS_PACKETLEN_MAXFL_Rst   0x40U    /* "maximum" frame length = 64   ?! */
```

The reset values are self-evidently absurd (a *minimum* frame length of 1536 and a *maximum*
of 64), which is the tell. **The RDL/header is wrong; the RTL is right.**

## Why it matters — this WILL break the board

Any driver or bench that programs `PACKETLEN` using these definitions writes the halves the
wrong way round. Writing "MAXFL=1518, MINFL=64" as `(1518 << 16) | 64` actually programs
**MINFL = 1518**, and the MAC then does exactly what it is told: it **pads every short frame
up to 1518 bytes** before appending the FCS.

So the *symptom* I originally reported is real and would hit real hardware — every ARP /
DHCP / ICMP packet leaving the MAC as a 1518-byte frame — but the cause is the register map,
not the MAC.

**Both benches have this bug today:**
- the reference cocotb: `cocotb/ethmac_ahb/test_basic_app.py:133` → `reg_write(REG_PACKETLEN, (1518 << 16) | 64)`
- this SUT (now fixed — see below).

This is also why my earlier "reference-confirmed" claim was worthless: the reference bench
reproduced the 1526-byte frame because it contains the *identical* programming error, not
because the DUT was broken. Two benches sharing one bug is not a confirmation.

## Proof the MAC is correct

With `PACKETLEN` written the right way round — `(MINFL << 16) | MAXFL` — the frame length
tracks the buffer descriptor exactly (`tests/lan8720_sut`, `VERDICT=PASS`):

| BD length | wire bytes | expected: `max(LEN+FCS, MINFL) + 8` |
|---|---|---|
| 46 | 72 | 72 (padded up to the 64-byte minimum) ✅ |
| 60 | 72 | 72 (60 + 4 FCS) ✅ |
| 100 | 112 | 112 ✅ |
| 200 | 212 | 212 ✅ |

Textbook behaviour: honour the BD length, pad short frames to MINFL, append the FCS.

The bench now **gates** on this (`ok TX frame length … = max(LEN+FCS, MINFL) + 8`), so the
regression cannot silently return.

**A second false finding fell with it:** the "RX BD ring does not advance" observation
(previously logged as unresolved) was the *same* root cause — with `MAXFL` mis-programmed to
64, frames were being aborted. The ring now advances correctly and is a passing gate.

## How the probe found it

`+TXDBG` traces the TX end-of-frame handshake on `MTxClk`. It showed the FSM leaving
`StateData` correctly on `TxEndFrm` and entering `StatePAD` — then padding forever because
`NibbleMinFl` never asserted:

```
ByteCnt=60 NibCnt=120 MinFL=1518 thr=3027 StateData=00 PAD=1 NibMinFl=0
```

`NibbleMinFl = NibCnt >= ((MinFL-4)<<1)-1` (`eth_txcounters.v:167`). With `MinFL` = **1518**
the threshold is 3027 nibbles — unreachable — so `StartFCS` (`StatePAD & NibbleMinFl & CrcEn`)
could never fire. `MinFL` being 1518 was the whole story.

## Action

1. **Fix the `ethmac_regs` RDL** (and regenerate `ethmac_regs.generated.h`): MINFL is
   `[31:16]` (reset 64), MAXFL is `[15:0]` (reset 1536).
2. **Fix the reference cocotb** (`test_basic_app.py:133`, and any other `PACKETLEN` writers).
3. **Audit any firmware/driver** using `ETHMAC_REGS_PACKETLEN_*_Pos` — it is programming the
   MAC backwards today.
4. This SUT is already fixed and gates on the frame length.
